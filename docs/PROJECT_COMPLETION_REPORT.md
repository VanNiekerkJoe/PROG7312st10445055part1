## What I built

Smart-X is a monitoring system for a fleet of small ESP32 sensors, the kind you would find on a hydroponic farm or a smart grid. The sensors send readings to a gateway, and an operator watches and controls them from a web dashboard. I built it in three parts on .NET 10: an API that uses SignalR to push live updates, a Blazor dashboard, a simulator that pretends to be the sensors, and a test project. Part 1 was about registering devices and taking in their readings. Part 2 added a live command stream so an operator can switch things on and off and undo a mistake. Part 3, this submission, adds the network view: how the sensors link to each other, how a reading finds its way back to the gateway, and what happens when a node fails. All three parts sit under one menu, Firebase sign-in protects every page and every request, and the solution has 73 automated tests that all pass.

## Part 1: getting the data in

The first problem was that readings come in different shapes. Moisture is a decimal, power use is a whole number and a valve is simply on or off. Storing them all as plain objects would have meant converting every reading on the way in, so I made the packet class generic and limited it to simple value types. That keeps it fast and lets the compiler reject anything that does not belong. The deployment itself is a tree of facility, zone, sub-zone and device, and a device only makes sense if everything above it is set up and its MAC address is unique. I wrote a recursive validator that walks the tree and returns a list of what is wrong, such as a duplicate MAC address, so the dashboard can tell the operator exactly what to fix. Importing a device list from a text file works the same way: each line is checked on its own, so one bad line does not throw away the rest, and the operator is told which line failed.

The constellation is the picture at the heart of Part 1. Every sensor is a dot on a radar, grouped into arcs by zone, coloured by how healthy it is, and dimmed when it does not match the operator's filter. Getting it right took several passes in the first week of September. I fixed the view and the sensor categories first, then did a second round on the drawing itself, because the node colours did not come out right until I reworked the CSS. The layout also has to cope with any number of devices, so it switches to a denser style once there are more than 28 sensors instead of drawing them on top of each other.

A radar is no use if a new sensor does not show up on it, so adding nodes properly was its own piece of work. I changed registration so the form loads from a cache, the new device appears on the radar the moment it is saved, a short flash and expanding ring show where it landed, and the form stays open so several devices can be registered in a row. That needed changes on both sides: the page and registration form, and the API's seeder and sensor endpoints, so a device added in the browser really exists on the server and is not only drawn. Removing devices needed the same care. Deleting or clearing in one browser tab has to purge the server's indexes, so other open dashboards do not keep showing the old nodes.

## Part 2: the live command stream

Part 2 had the most moving parts. Critical alerts needed to jump the queue, but the built-in priority queue does not promise to keep arrival order when two items have the same priority, so I added a sequence number as a tie-breaker. Undo was trickier than it sounds. If the opposite command that undo sends were itself added to the undo history, pressing undo repeatedly would just flip a device back and forth, so those commands are logged but never stacked.

A busy fleet can send thousands of packets at once. To stop that freezing the browser, the API only checks and queues each packet, a background worker handles a fixed number every tenth of a second, and the dashboard hears about each device once per cycle instead of once per packet. Plain HTTP has no "device went quiet" message, so a sweep every few seconds marks any device that has been silent for 20 seconds as disconnected. The suggestion feature learns what operators usually do, and I changed it so that applying a suggestion does not count as something the operator chose, otherwise it would keep reinforcing itself.

Adding Firebase sign-in caused a problem that was hard to diagnose. The dashboard kept saying it could not contact Firebase, and that message was too vague to act on. The first thing I did was change the sign-in handler and the API client so they show the real status and details of any rejection instead of hiding them. Once the real response was visible, the cause was clear: the API's CORS settings only allowed the https address of the dashboard, not the http one, so the browser blocked the request. Allowing both addresses fixed it. A second sign-in issue was that browsers cannot attach a normal authorisation header to a live WebSocket connection, so for the live-update connection only, the token is passed in the address instead. Finally, switching between pages used to reset the live data, so I moved it into one shared service that lives as long as the app.

## Part 3: the mesh network

Part 3 started with history. Until then I could only ask for the latest readings, but the brief needs everything between two times. I replaced the sorted dictionary with an AVL tree that I wrote myself. It is a tree that keeps itself balanced, so a lookup by time only walks the part of the tree it needs. In a test with 20,000 readings, a window of 100 readings touched about 115 entries instead of all 20,000, and even 10,000 readings added in time order, which would ruin an ordinary tree, left it only 14 levels deep.

There is no real radio data, so the links between sensors are generated from the deployment tree in a fixed way, which means the same sensors always give the same mesh. Each link has a cost that stands in for transmit power. The mesh is stored as a graph, and a breadth-first or depth-first search from the gateway shows which sensors can still be reached. I had to decide what "down" means. A sensor can be down itself, or it can be fine but cut off because every route to the gateway passes through a failed one. The app shows these separately and, for each affected sensor, shows the new route next to the old one.

To find the cheapest way to connect every sensor to the gateway I used Prim's algorithm, built on a small heap I wrote. As a check I also implemented Kruskal's algorithm, and the two agree on 100 randomly generated meshes in the tests. The cheapest network overall is not always the cheapest route for one particular sensor, so I also added Dijkstra's algorithm, and the route panel shows both.

Putting this on the Blazor page had small hurdles of its own. Razor treats the word `text` as one of its own tags, which broke the labels in the SVG drawing until I wrapped each one in a group element. Numbers in a culture that uses a decimal comma would also produce invalid SVG, so the coordinates are always formatted the same way.

## What I learned

The biggest lesson was to choose a data structure for the question being asked. The same history data needed a different tree once the question changed from "the latest readings" in Part 2 to "readings between two times" in Part 3. Writing the algorithms by hand also taught me not to trust a single example. Instead I tested them against each other, such as Prim against Kruskal, and against simple rules like "a failed node never appears in a route". Deciding the failure rules first, down or cut off, kept the rest of the code simple. The Firebase problem taught me to make errors visible before guessing at causes, because a vague message was hiding what turned out to be a simple CORS setting. Across all three parts, ordering mattered too: the queue tie-breaker, the fixed link costs and consistent tie-breaking inside the algorithms all exist so the tests give the same answer every run. Finally, I try to be open about what is simulated, such as the link costs and the in-memory history, so nobody mistakes them for real measurements.

## What I would do differently

I would plan the history store around time ranges from Part 2. I used a sorted dictionary because Part 2 only needed the latest readings, and then had to replace it with an AVL tree in Part 3 when the brief asked for everything between two times. The swap was easy because history sat behind its own small class, but asking what question someone would eventually ask of the data would have saved the rewrite.

## Testing and what comes next

`dotnet test` runs 73 tests and all pass, 19 of them for Part 3. They cover the tree staying balanced, range queries, the heap, Prim against Kruskal, Dijkstra against the tree route, BFS and DFS, healing around a failed node, and looking up a route by MAC address. If I carried the project on, I would use real signal strength for the link costs, store history in a database so it survives a restart, accept readings over MQTT or a cloud service, and run more than one copy of the API. These ideas are explained in the technology recommendations.
